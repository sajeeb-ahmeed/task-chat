## Swagger coverage

The frontend implements these eight REST operations with the documented paths and request fields:

- `POST /auth/login`, `GET /auth/me`
- `GET /users/search`
- `GET /conversations`, `POST /conversations`
- `POST /conversations/group`
- `GET /conversations/{id}/messages`
- `POST /messages`

REST calls use `/api` and Bearer authentication. Socket.io connects to the root origin with `auth.token`; the app handles `message:new` and `conversation:updated`. REST sending is permitted by the specification; using it instead of emitting `message:send` is not a compliance failure.

Four group management operations are documented but have no frontend controls/API methods and were not live tested: add participants, remove participants/leave, promote admin, and rename group. These are Swagger capability gaps, not omissions from the PDF's explicit group creation/messaging requirements.

`GET /api/health` is unused and returned 404 again during this review. It is a supplied-backend discrepancy, not a broken frontend feature.

## Findings

### QA-01 — High: phone normalization can select a different identity

Location: `src/lib/api.ts` login adapter and `src/lib/identity.ts`.

The UI accepts a plus-prefixed international number, but the adapter removes the plus before login. A synthetic API probe in this review registered a plus-prefixed number, then logged in with its digit-only equivalent. The backend returned different user IDs (`same_user_after_frontend_normalization: false`). Therefore an existing backend user may enter their stored number in Thread and receive a new account instead of their original conversations. Digit-only exact search also cannot find the plus-prefixed stored identity.

The current live browser test covers a formatted search for a user whose stored number is already digit-only. Passing that test does not cover this existing-account case. The README describes the search limitation but understates the login consequence.

Suggested correction: agree on identity-preserving normalization with the backend; do not silently change an existing login identifier to work around search. Add a regression case for an account stored with `+`. Keep search error handling separate from login identity handling.

### QA-02 — Low: formatting check fails

`npm run format:check` exits 1 for:

- `src/app/globals.css`
- `tests/live-chat.spec.ts`
- `package.json`

This is a code consistency issue, not a demonstrated runtime failure. Format the files and rerun the check in a separate maintenance change.

## Design freedom

Part 2 explicitly states: “No design file will be provided for this part — the visual direction is entirely up to you.” Layout, palette, typography and interactions are the candidate's decisions. The landing page must be responsive and clearly showcase the feature; original work is encouraged over a generic template.

Part 1 supplies functional and usability constraints, not a visual mockup or mandatory palette. The candidate can choose the chat design while maintaining clear sender distinction, timestamps, loading/empty/error feedback, realtime delivery and reading-position behavior. The PDF specifically prioritizes polish of the chat panel.

The current off-white/green design is a permissible direction, not an employer-mandated design. It can be redesigned to the candidate's preference while preserving the tested behavior. Bonus credit is evaluator-dependent; an interactive preview or a required auto-scroll behavior should not be represented as guaranteed originality credit.
